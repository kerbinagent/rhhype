# Streaming book protocols

The paper monitor uses `scripts/paper_streams.py` with `StreamManager(session, markets, on_book, on_status).run(stop)`. It runs public, read-only sockets. `on_book` receives a full sorted book view (up to `max_levels` per side), receipt time, engine/event time when the venue exposes one, sequence, reconnect generation, and `valid`. Every disconnect, crossed book, overflow, or detected gap emits `valid=False` and clears cached state. Callbacks run synchronously in the reader task and should stay quick.

| Venue | Feed | Reconstruction |
|---|---|---|
| Hyperliquid native and xyz | [`l2Book` snapshots](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/websocket/subscriptions) at `wss://api.hyperliquid.xyz/ws` | Every update is a fresh book with exchange millisecond time; no sequence claim. `activeAssetCtx` also supplies a current oracle price, timestamped at receipt because the context message has no server timestamp. |
| Lighter Core | [`order_book/{market_id}`](https://apidocs.lighter.xyz/docs/websocket-reference#order-book) at `wss://mainnet.zklighter.elliot.ai/stream?readonly=true` | Subscription snapshot, then absolute price-level updates. `begin_nonce` must match previous `nonce`; `offset` need not be continuous. Gap forces unsubscribe and resubscribe. `market_stats/{market_id}` supplies mark, index, and funding fields separately. |
| Robinhood Lighter | Same Lighter protocol at `wss://api.rh.lighter.xyz/stream?readonly=true` | Independent market namespace and state. The public [deployment endpoint](https://nautilustrader.io/docs/latest/integrations/lighter/) and live subscribed/update envelopes were verified. |
| Aster | [`@depth@100ms` diffs](https://github.com/asterdex/api-docs/blob/master/V3%28Recommended%29/EN/aster-finance-futures-api-v3.md#diff-book-depth-streams) at `wss://fstream.asterdex.com` | Buffer changes while fetching a 1,000-level `/fapi/v3/depth` snapshot. The first diff must bridge the snapshot ID; subsequent `pu` must equal prior `u`. The first diff's `pu` may predate the REST snapshot. `@markPrice@1s` supplies reference mark/index and estimated funding. |

The Aster REST bootstrap is paced globally to at most 30 snapshot starts per minute and has a 4,096-event per-market buffer. Lighter retains up to 5,000 price levels per side; exceeding this invalidates the book instead of silently losing deeper levels that could later move into the displayed top levels. Hyperliquid snapshots have at most 20 levels per side. Socket groups contain at most 50 Hyperliquid, 25 Lighter, or 30 Aster markets. Aster groups use two streams per market, below its [200-stream socket limit](https://github.com/asterdex/api-docs/blob/master/V3%28Recommended%29/EN/aster-finance-futures-api-v3.md#websocket-market-streams).

On 2026-09-29, short public connection checks confirmed all four live subscription envelopes. A subsequent nine-second Aster integration run reconstructed 75 valid BTCUSDT books with no sequence-gap invalidation. These checks validate protocol handling, not order execution or data completeness during later venue outages.

## Hyperliquid execution refresh

During a later live check, Hyperliquid `l2Book` WebSocket snapshots for BTC, XPL, and three xyz markets arrived together about every **5.2 seconds**. Seven spaced public REST `l2Book` requests returned advancing engine timestamps about 0.35–0.83 seconds old. A three-second paper order timeout therefore needs a targeted REST refresh to see a new Hyperliquid book after its configured delay. `scripts/paper_refresh.py` uses the shared, rate-gated monitor client only for due Hyperliquid entry/exit intents, due latency probes, and held Hyperliquid exposure. It caps work at three concurrent requests and one request per key per 0.5 seconds, rotates priority classes, and keeps at most 1,024 recent scheduler keys. A response is discarded if the stream generation changed or a newer book arrived while the request was pending. REST failure leaves the stream book untouched.

The all-market integration later observed around 734 book events per second, nine open paper positions and zero hedge failures/timeouts after targeted refresh was enabled. This is a short operational validation, not a measurement of trade profitability.
